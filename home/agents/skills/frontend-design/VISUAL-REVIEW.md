# Diagnose the rendered interface

Inspect the screen inside the product's chosen visual direction. Follow the task from the first information the user needs to the resulting action and feedback. Use these questions to locate a problem rather than applying every visual preference to every page.

- **Priority:** Can the user identify the important status and primary action? If several elements compete, change their emphasis to match the task.
- **Relationships:** Do spacing and alignment reveal which labels, values, and controls belong together? Inspect both dense and sparse content.
- **Reading:** Does type size, line length, and variation make the structure readable? Check realistic text instead of only short placeholders.
- **Color:** Is text readable against its background, and does each status color retain the same meaning? Verify that color alone does not carry necessary information.
- **Product fit:** Do related controls and surfaces use the product's existing tokens and patterns? Investigate an inconsistency before introducing another local style.
- **Interaction:** Can the user recognize enabled, pending, selected, and failed states that occur here? Exercise keyboard navigation and inspect focus.
- **Content agreement:** Do labels, totals, summaries, and resulting messages describe the same outcome? A polished layout can still communicate the wrong result.
- **Adaptation:** At affected widths, does content preserve order and usable controls without overlap or accidental clipping? Include the states that change density.
- **Motion:** Does movement explain a change, and does reduced motion retain the information without unnecessary movement?

Fix the observed cause, then revisit the same task and state at the affected width. A screenshot of the initial screen does not verify an open menu, a submitted form, or a pending operation.
